## 1. Summary

- Overall assessment: the operation layer is tight where it is stateful and loose where it is cross-chain. Every one of the eleven operations has a stateless check, a stateful check against the state its predecessors in the same transaction left, and an execution step, in that order, and every replay guard that the specification asks for within one chain (note consumption, channel parents, declaration nonces, voucher and puzzle nullifiers) is present at this commit. What is absent is any chain identity in any signing domain: the transaction hash is a Blake2b of the operation column alone, every ZK signature, Ed25519 signature, channel multi-signature and proof of claim commits to that hash and nothing else, and the `chain_id` that the genesis specification puts in the inscription "to guarantee that the networks are disjoint" is read by the node only to serve it on the HTTP API and the FFI. Because a note's identifier is a function of the operation that created it and not of the chain, two networks built from the same stakeholder list hold byte-identical genesis notes, and every transaction that spends one of them is valid on both networks with the same recipient. The fee logic is sound: a transaction can only fund its fee through a `Transfer`, the balance check is signed 128-bit arithmetic and fails closed, and no operation is fee-free because storage gas is charged per byte at a price that never falls below 1. The size limits hold before decoding on every network ingress; the one post-decode check, the 2 MiB block body, is made harmless by the sync frame bound.
- Findings: 0 critical · 0 high · 1 medium · 0 low · 1 informational
- Key themes: "the transaction hash is the whole signing domain, and it names no chain", "genesis note identifiers are a function of the stakeholder list alone", "within one chain every operation has its replay guard".
- Must-fix before launch: LB-001, before any network is started from a stakeholder file that another network has used or will use. The cheapest fix is a chain-bound transaction hash (S-001), which is a specification change to `bedrock-v1.1-mantle-specification.md` §Mantle Transaction and a one-line change to the hasher; the code-only alternative is to mix the genesis block identifier into the note identifier derivation, which is also a specification change.

Answers to the five checklist items, in order:

1. **Every op type: validation, authorisation, ordering (§4.1).** Verification is one linear pass per transaction: `VerifiedOperations::next` (`core/src/mantle/transactions/verified_ops.rs` L48-L60) verifies operation `i` against a `MantleOperationVerificationHelper` rebuilt from the state operations `0..i` left (`ledger/src/lib.rs` L943-L951), prices it (L964-L968), then executes it (L970-L976); the ZK proofs are collected and batch-verified after the whole block (`chain-service/src/lib.rs` L461-L478, `core/src/mantle/batch.rs` L45-L69). The table in §4.1 gives, per operation, the proof type, who it authorises, where the proof is checked (`preverify` at decode, `verify` against state, or the deferred batch), the state-dependent checks, and the within-chain replay guard. Three cells are known defects from prior reports and are cited, not re-reported: `ClaimPowReward` carries no proof at all (#167 LB-001) and costs 1 gas (#636 LB-006); `ChannelConfig` does not bound its thresholds by the key count (#185 LB-001); a non-sequential SDP nonce can strand a declaration (#53 LB-001). Two new observations are in §5: `LeaderClaim` verifies its Groth16 proof twice (S-003) and a block that repeats a transaction is rejected by the second copy's input check, as the specification requires, but only because every transaction must carry a `Transfer` (S-004).
2. **Transaction hash covers all fields (§4.2).** By specification it does not: `mantle_txhash` is `Blake2b-256("MANTLE_TXHASH_V1" || encode(ops))` over the operation column only (`tx_list/hash.rs` L6-L9, `signed_ops.rs` L242-L251, test `changing_a_proof_does_not_change_the_transaction_hash` L855-L882), and the proofs are bound to the transaction by taking that hash as their message, not by being hashed (`bedrock-v1.1-mantle-specification.md` L114). Within the operation column the encoding is canonical (fixed-width little-endian integers, length-prefixed lists, trailing bytes rejected, `signed_ops.rs` L933-L940), so no two operation columns share a hash; #56 and #744 cover the codec side. The consequence of excluding the proofs, a proof-mangled copy of a transaction shadowing the genuine one in the mempool and condemning the honest block, is #113 LB-001 (High), re-verified here only on the hashing side; the mempool side is unchanged in what this report read.
3. **Replay across forks, after reorg, across networks; chain-id binding (§4.3, LB-001).** Across forks and reorgs a transaction is replayable by design: the UTXO model makes the second inclusion fail on consumed inputs, and #50 and #138 cover the re-broadcast side. Across networks nothing prevents it. The `expose-chain-id` work the issue flags is, at this commit, a `ChainId` type in the genesis inscription (`genesis_tx.rs` L241-L250), a getter that reads it off the genesis block (`config/cryptarchia/deployment.rs` L38-L43), an HTTP route (`api/handlers.rs` L492-L493) and an FFI getter (`c-bindings/src/api/chain.rs` L41-L56). No signing or verification path reads it: the transaction hash names no chain, the ZK signature public inputs are 32 public keys and that hash (`zk/proofs/zksign/src/public.rs` L6-L17), the Ed25519 and channel multi-signatures sign the hash bytes (`inscribe.rs` L138-L141, `verification.rs` L37-L46), and the proof of claim takes the hash as `mantle_tx_hash` (`leader_claim.rs` L228-L232). A "malformed or mismatched chain-id" therefore cannot fail closed, because nothing compares one. What keeps networks apart is the note identifier, and it is derived from the creating operation alone (`core/src/mantle/ledger.rs` L512-L530; genesis notes from the genesis transfer at `ledger/src/cryptarchia/mod.rs` L716-L742), so it does not keep apart two networks built from the same stakeholder list. That is LB-001.
4. **Fees (§4.4).** The payer is whoever signs the `Transfer` operations of the transaction: `balance` accumulates only the input-minus-output difference of `Transfer` ops (`ledger/src/lib.rs` L876-L886, `cryptarchia/mod.rs` L573-L589); `LeaderClaim` and `ClaimPowReward` create a note but add nothing to the balance, so a claim pays by spending its own reward note in a later `Transfer` of the same transaction, which the interleaved verification allows and the PoW service relies on (`services/pow/src/service.rs` L1312-L1315). The fee is `execution_gas × base_fee + bytes × storage_price` and is deducted once, after all operations executed, by the check `balance < total_gas_cost` at L510-L512, where `balance` is `i128` and the cost is `u64`, so a transaction whose outputs exceed its inputs, or whose fee exceeds its surplus, fails closed with `InsufficientBalance`; the block-level gas limit is enforced per transaction and cumulatively (`gas_and_fees.rs` L30-L44). No operation is fee-free: a channel-creating `ChannelConfig` costs 0 execution gas (`config.rs` L191-L198, test `signed_ops.rs` L682-L695) but every transaction pays storage gas equal to its encoded length at a price with a floor of 1 (`update_storage_market` rounds up, `cryptarchia/mod.rs` L822-L832; `overview-cryptoeconomics.md` L94), so a transaction without a `Transfer` has balance 0 and is rejected. The one arithmetic wart is LB-002: the tip is computed from `balance as Value`, a truncating cast, which only the holder of the `u64::MAX` faucet note of the testnet template can trigger and which only understates that holder's own tip.
5. **Size limits (§4.5).** Every network ingress bounds bytes before decoding: gossip transactions at `MAX_BLOCK_TRANSACTIONS_SIZE + 8` (`tx-service/.../libp2p.rs` L24-L30), HTTP bodies at 10 MB (`api-common/src/settings.rs` L25-L45, applied at `api/backend.rs` L224-L231), block proposals at their fixed maximum of 18,192 bytes (`core/src/block/mod.rs` L146), sync frames at a bound derived from the block limits (`cryptarchia-sync/src/libp2p/messages.rs` L27-L42). Counts are enforced by the decoders' bounded vectors: 255 ops per transaction (`transactions/mod.rs` L40, `tx_list/common.rs` L7), 255 inputs and outputs per operation (`ledger.rs` L36-L40), 1,024 transactions per block (`block/mod.rs` L31, L183), 4 uncles. The block body's 2 MiB check runs after the transactions are decoded (`block/mod.rs` L272-L295), which is acceptable only because the sync frame bound above caps what can be handed to the decoder; the mempool's own 2 MiB item check also runs after decode (`tx/service.rs` L527-L531) behind the pre-decode gossip bound. Where an inner field is bounded far above what a valid message can hold (`Inscription` at 7/8 of 2 MiB, `Metadata` at `u32::MAX`), the outer pre-decode bound is what protects allocation, which #56 LB-002 and #69 LB-002 already describe.

### 4.1 Item 1: what each operation checks, and who may execute it

The pipeline is the same for every operation. Decoding pairs each operation with a proof of the type its opcode requires (`op_proof.rs` L33-L47; a mismatch is `OpProofMismatch`, `signed_ops.rs` L49-L61). `preverify` runs stateless checks with only the transaction hash in hand (`signed_ops.rs` L123-L130). `verify` runs against the state left by the preceding operations of the same transaction, through a helper rebuilt before each operation (`ledger/src/lib.rs` L943-L951); a failure ends the transaction (`verified_ops.rs` L28-L35). Execution follows immediately (L970-L976). ZK proofs are not verified inline: `verify` returns a `DeferredZkpVerification` with the public inputs taken from the state the operation was verified in, and the block verifies all of them in two batches at the end (`batch.rs` L45-L69). The helper reads the tip state's channels, service notes, UTXO tree, declarations, nullifiers, voucher root, epoch and slot (`verification_helper.rs` L22-L94).

What was checked and ruled out for item 1:

- **Authorisation is never bypassed by the state the helper reads.** Each stateful check reads the helper's view of the state after the preceding operations, so an operation can authorise itself only with what earlier operations in the same transaction legitimately produced: a `ChannelWithdraw` after a `ChannelDeposit` in one transaction releases notes the deposit re-created, under the channel's keys; a `Transfer` after a `LeaderClaim` spends the reward note under the claimant's `pk`; an `SDPActive` after an `SDPDeclare` in one transaction is rejected, because the declaration's `active` epoch is set at execution and the activity check reads it (not exercised here, but the ordering is by construction).
- **Ordering inside a block** is the sequential application of `try_apply_block_contents` (`ledger/src/lib.rs` L539-L546), matching `bedrock-v1.1-block-construction.md` §Mempool Transactions Validation. A transaction consuming a note an earlier transaction created is valid in that order; two transactions spending the same note make the block invalid whatever their order, since `Inputs::validate_not_in_service_and_present` fails on the second. A block that contains the same transaction twice fails the same way, because every transaction carries at least one `Transfer` with at least one input (S-004 explains why that is the only reason).
- **Proof type confusion is impossible after decode.** `decode_for_op` picks the decoder from the opcode (`op_proof.rs` L33-L47), and `from_parts` rejects a proof of the wrong variant with the index of the mismatch (`signed_ops.rs` L49-L61, test L589-L606). The JSON path goes through the same `from_parts` (L366-L379).
- **The `Verified` state is only reachable through `verify`** outside genesis: `into_state_trusted` is `pub(crate)` and documented as genesis-and-tests only (`signed_ops.rs` L182-L198); `GenesisTx::deserialize` is the one production caller (`genesis_tx.rs` L230-L239), and #53 LB-003 records what genesis mode skips.

### 4.2 Item 2: what the transaction hash covers

`mantle_txhash = Blake2b-256("MANTLE_TXHASH_V1" || encode(MantleTx))` where `MantleTx` is the operation column (`tx_list/hash.rs` L6-L9 over `as_signing`, which is `op_refs().as_signing()` at `signed_ops.rs` L248-L250; test vectors in `ops/mod.rs` L48-L52 and #245). The proof column is excluded on purpose: the specification binds each proof to the transaction by making the hash the proof's message (`bedrock-v1.1-mantle-specification.md` L114), so including the proofs in the hash would be circular for the ZK signatures. Inside the operation column nothing is malleable: integers are fixed-width little-endian, every list is length-prefixed with a fixed-width count, the two columns share one count (`signed_ops.rs` L201-L222), and a decoder consumes its input exactly (`deserialize_from_binary_rejects_trailing_bytes`, L933-L940; #56 LB-001 found and #744 re-swept the serde bridges). An `Op` therefore has one encoding and one hash.

What the exclusion of the proofs costs is not new: two signed transactions with the same operations and different proofs share the hash, the reference prefix, the Merkle leaf in `body_root` and the mempool key, and #113 LB-001 shows how a proof-mangled copy shadows the genuine transaction and makes nodes reject the honest block. This report re-verified the hashing side at `273658c7` (`signed_ops.rs` L242-L251, L855-L882) and did not re-read the mempool; the mitigation #113 recommends (verify the proofs at admission, or key the pool by the full bytes) is unchanged in what was read.

Dynamic check: the core crate's unit tests for `transactions::tx_list::signed_ops`, `ops::transfer` and `ops::channel::inscribe` pass at `273658c7` (47 passed, §3), including `changing_a_proof_does_not_change_the_transaction_hash`, `deserialize_from_binary_rejects_trailing_bytes`, `from_parts_reports_the_index_of_the_mismatched_proof`, `preverify_rejects_a_signature_over_another_transaction` and `execution_gas_of_a_channel_creating_config_is_zero`, which pin the properties this section and §4.4 rely on.

### 4.3 Item 3: replay across forks, reorgs and networks

**Within one chain.** Every operation has a state-side guard against a second inclusion (the last-but-one column of the table in §4.1): consumed inputs for `Transfer`, `ChannelDeposit` and `ChannelTransfer`; the message and configuration parents for `ChannelInscribe` and `ChannelConfig`; strictly increasing nonces for `SDPWithdraw` and `SDPActive`; the payload hash for `SDPDeclare`; nullifiers for `LeaderClaim` and `ClaimPowReward`; channel membership for `ChannelWithdraw`. A transaction that appears on two forks or is re-included after a reorg is the UTXO model working as intended; the second inclusion on the same chain fails, and the re-broadcast amplification on reorg is #50 and #138.

**Across networks.** Nothing. The full signing domain of a transaction is its hash, and the hash is a function of the operation bytes. The specifications at `d788723` say nothing about a chain identifier in the transaction (`mantle-transaction-encoding.md` has no such field; the Mantle spec's replay sentence at L114 is about binding proofs to the transaction) and place the only chain identity in the genesis inscription, where it is meant "to guarantee that the networks are disjoint" (`bedrock-genesis-block.md` L120). The code matches: LB-001.

| Target | `core/src/mantle/transactions/tx_list/hash.rs:L6-L9` (hash over the operation column only); `core/src/mantle/ledger.rs:L512-L530` (`Utxo::id`: `NOTE_ID_V1`, `op_id`, index, value, `pk`) and `core/src/mantle/ops/op.rs:L30-L34` (`op_id` = Blake2b of the operation payload); `ledger/src/cryptarchia/mod.rs:L716-L742` (genesis notes from the genesis transfer alone); `core/src/mantle/transactions/genesis_tx.rs:L241-L250` (`ChainId` lives in the inscription); `nodes/node/binary/src/config/cryptarchia/deployment.rs:L38-L43` and `nodes/node/binary/src/api/handlers.rs:L492-L493` (the only consumers) |
| Status | Open |

**Description**

A signed Mantle transaction commits to its operations through `mantle_txhash`, and every proof it carries commits to that hash: the ZK signature's public inputs are the input public keys and the hash (`zk/proofs/zksign/src/public.rs` L6-L17; `transfer.rs` L157-L159), the inscription's Ed25519 signature is over the hash bytes (`inscribe.rs` L138-L141), the channel multi-signatures are over the hash bytes (`verification.rs` L37-L46), the SDP proofs take the hash as message (`declare.rs` L207-L209, `withdraw.rs` L123-L126, `active.rs` L96-L98), and the proof of claim takes it as `mantle_tx_hash` (`leader_claim.rs` L228-L232). No preimage anywhere in that chain contains the genesis block identifier, the `chain_id`, or anything else that differs between two networks running the same software. The `chain_id` the issue's ⚑ item refers to exists at this commit as a bounded UTF-8 string in the genesis inscription, decoded at `genesis_tx.rs` L241-L250, read back by `DeploymentSettings::chain_id` (`deployment.rs` L38-L43), served on `GET /chain_id` (`handlers.rs` L492-L493) and through the FFI (`c-bindings/src/api/chain.rs` L41-L56), and used nowhere else; a mismatched or malformed value cannot fail closed because no verification path compares one.

What separates networks in practice is that a transaction references state: note identifiers, channel identifiers, declaration identifiers. A note identifier is `zkhash(NOTE_ID_V1, op_id, output_index, value, pk)` with `op_id = Blake2b(OPERATION_ID_V1 || encode(op))` (`ledger.rs` L512-L530, `op.rs` L30-L34; spec §Note Id), so it depends only on the operation that created the note. The genesis notes are created by the genesis transfer, whose payload is its output list (`genesis_tx.rs` L65-L80: no inputs; `cryptarchia/mod.rs` L716-L736), so two networks whose genesis transfers list the same `(value, pk)` pairs in the same order have the same genesis note identifiers, whatever their `chain_id`, `genesis_time` or nonce say (#45 L141 made the same observation for the nonce-grinding case). Every transaction that spends only such notes then verifies on both networks, and the notes it creates have identical identifiers on both, so the coincidence propagates through every replayed transaction. Channel identifiers are chosen by users and identical by construction; a declaration identifier is a hash of the declare payload and is identical when the service note is.

The precondition, a shared stakeholder list, is the ordinary way a rehearsal or a long-lived test network is set up: the ceremony (`tools/blockchain-tools/src/bin/genesis.rs`, #201 §4) takes the stakeholder file as its input, and nothing in the templates or the tooling derives anything network-specific into the notes. The three templates differ only in `chain_id` and in the reward and stake parameters.

**Exploit scenario**

A rehearsal network is started from the stakeholder file prepared for the production network, as a dress rehearsal of the ceremony, with `chain_id = "X.Y.Z-rc.N"`. A stakeholder uses a wallet against the rehearsal to test a payment: a `Transfer` spending one genesis note to a recipient key, with change. The signed transaction is gossiped on the rehearsal network and is public. Anyone who observes it, or the rehearsal's block history later, submits the same bytes to the production network once it is live: the input note exists there with the same identifier and the same `pk`, the ZK signature verifies against the same public inputs, the fee is covered by the same surplus, and the production notes move to the same recipient key and change key. The victim did not intend a production payment, and the recipient may be a key the victim controls only on the rehearsal, a test key it has since discarded, or a counterparty that was only ever meant to receive test tokens. The same replay applies to a `ChannelDeposit` (the production notes become channel notes of a channel that may not exist there yet, which the deposit's verify rejects, or of one that does, which it accepts), to an `SDPDeclare` (the production note is locked as collateral under the rehearsal's locators), and to an `SDPWithdraw` (the production declaration is withdrawn). An attacker needs no key and no stake; the replay costs the victim's fee. The window is unbounded: a rehearsal transaction from months earlier replays on the day the production network starts, before the victim has moved anything.

**Recommendation**

- *Short term*: bind every transaction to its chain in the one place all proofs already commit to: make the transaction hash `Blake2b-256("MANTLE_TXHASH_V1" || genesis_block_id || encode(MantleTx))`, with the genesis block identifier (a derived value, which #182 S-001 also prefers over the typed `chain_id`) read from the ledger configuration. This is a change to `tx_hasher` and to every signer (the wallet, the PoW service, the zone SDK, the testing framework), and a specification change to `bedrock-v1.1-mantle-specification.md` §Mantle Transaction and to `mantle-transaction-encoding.md` (S-001). Until it ships, never start a network from a stakeholder file another network has used, and say so in the ceremony documentation.
- *Long term*: also mix the genesis block identifier into `derive_note_id` (a sixth field in the `zkhash`), so that no two networks share a note identifier even for notes created by byte-identical operations; that closes the same gap for anything that identifies state by note identifier outside a transaction (proof-of-leadership inputs, checkpoint files, wallet databases keyed by note id). This touches the proof-of-leadership circuit and is the larger change.

**References**: `bedrock-v1.1-mantle-specification.md` §Mantle Transaction (L114), §Note Id (L1855-L1879); `bedrock-genesis-block.md` §Cryptarchia Parameters (L119-L120); `mantle-transaction-encoding.md` (no chain field); #53 B19 (deferred here); #45 L141 (note identifiers independent of `chain_id`); #175 LB-002, #38 LB-001, #182 S-001 (consensus parameters and namespace not bound to the chain; the same theme at other layers); #201 §4 (the ceremony's inputs).

### 4.4 Item 4: fees

`try_apply_transaction` (`ledger/src/lib.rs` L484-L524) applies all operations first, accumulating `balance: i128` and `execution_gas: Gas`, then prices the transaction at the tip's prices (L495-L500): `execution_gas × execution_base_gas_price + storage_size × storage_gas_price`, all in `u64` with `checked_mul` and `checked_add` (`gas.rs` L80-L85, L92-L94). If `balance < total_gas_cost` the transaction is rejected with `InsufficientBalance` (L510-L512); since the cost is non-negative, this also rejects every transaction whose outputs exceed its inputs. The cost is then the burned fee and the remainder the tip (L514-L515). `GasAndFees::checked_add` (`gas_and_fees.rs` L30-L52) rejects a transaction whose own execution gas exceeds the block limit and a block whose cumulative execution gas does, and sums the storage gas and fees with checked arithmetic. Block rewards and the execution and storage market updates read the sums (L548-L558).

| Question | Answer at `273658c7` |
|---|---|
| Who pays | The signers of the transaction's `Transfer` operations: only `SignedOp::Transfer` changes `balance` (`lib.rs` L876-L886). |
| When deducted | Once per transaction, after all its operations executed and before the next transaction (L510-L515, L539-L546); a failing transaction fails the block and nothing is deducted (`bedrock-v1.1-block-construction.md` §Block Proposal Validation, last paragraph). |
| Fee > balance | `InsufficientBalance`; `balance` is `i128` so a negative surplus cannot wrap. |
| Underflow anywhere | None on the checked path. The one unchecked cast is LB-002. |
| Fee-less operations | None. `ClaimPowReward` charges 1 gas (#636 LB-006) and a channel-creating `ChannelConfig` charges 0 execution gas (`config.rs` L191-L198; test `signed_ops.rs` L682-L695), but storage gas is `storage_size()` bytes at a price that starts at 1 (`transactions/gas.rs` L9) and is updated with rounding up so it never reaches 0 (`cryptarchia/mod.rs` L822-L832; `overview-cryptoeconomics.md` L94). A transaction with no `Transfer` has balance 0 and a positive cost, and is rejected. |
| Claims funding themselves | A `LeaderClaim` or `ClaimPowReward` adds a note, not balance; the claim pays by spending that note in a later `Transfer` of the same transaction, which the interleaved verify-then-execute allows (the note is in `latest_utxos` when the transfer is verified). The PoW service builds exactly that shape (`services/pow/src/service.rs` L1312-L1315). |
| DoS through cheap operations | Bounded by storage gas per byte and by the block byte limit; the execution-gas side of `ChannelConfig` and `ChannelInscribe` is what makes the storage market the binding one for those (`overview-cryptoeconomics.md` L96, L116). The mis-priced note insertion of #178 S-003 is #630's subject and not re-examined here. |

### LB-002 · The fee tip is computed from a truncating `i128 → u64` cast of the transaction balance

| | |
|---|---|
| Severity | Informational |
| Difficulty | High |
| Category | Data Validation |
| Target | `ledger/src/lib.rs:L515` (`GasCost::from(balance as Value).checked_sub(fee_burned)`) |
| Status | Open |

**Description**

After the check `balance >= total_gas_cost` (L510-L512), the tip is `GasCost::from(balance as Value) - fee_burned` (L515). `balance` is `i128` and `Value` is `u64`; the cast truncates when the surplus exceeds `u64::MAX`. `Inputs::amount` and `Outputs::amount` are `checked_add` over `u64` (`ledger.rs` L377-L388, L182-L190), so a single `Transfer` cannot exceed `u64::MAX`, but the transaction sums up to 255 transfers in `i128` (`lib.rs` L882-L884), and the testnet template's faucet note is worth `u64::MAX` on its own (#201 §4, `deployment/ceremony/genesis/testnet/*`). A transaction with two transfers, one spending the faucet note and one spending any other note, has a surplus above `u64::MAX` if its outputs are small. The truncated value is then either below `fee_burned`, in which case `checked_sub` fails with `GasOverflow` and the transaction is rejected, or above it, in which case the tip is the truncated surplus minus the fee and the difference between the true surplus and the tip is neither burned, nor tipped, nor conserved: it leaves the ledger's accounting (the notes are consumed; the block reward computation sees a smaller `fee_tip`).

**Exploit scenario**

Only the holder of the faucet key can build such a transaction, and the value that disappears is the holder's own surplus, so there is no attacker. The point is that the invariant "inputs = outputs + burned + tipped" does not hold for one reachable class of transactions on the testnet template, and that `as_conversions` being allowed (#19) is what lets it compile without a warning.

**Recommendation**

- *Short term*: compute the tip in `i128` and convert with `u64::try_from(...)`, rejecting the transaction (or saturating, with the difference burned) when the surplus does not fit; or reject a transaction whose `balance` exceeds `u64::MAX` at L510 alongside the insufficient-balance check.
- *Long term*: a per-transaction `Balance` type with a checked `into_tip()` would make every future use of the surplus go through the same check.

**References**: #19 (allowed casts); #201 LB-001 and §4 (the faucet note and the undefined token unit).

## 5. Suggestions (non-security)

### S-001 · Spec: give the transaction hash a chain-specific domain

`bedrock-v1.1-mantle-specification.md` §Mantle Transaction defines `mantle_txhash` over the encoded `MantleTx` with the constant `MANTLE_TXHASH_V1`, and L114 explains the binding of the proofs to that hash as the replay protection. It protects against replaying a proof under another transaction, not a transaction under another network. Add the genesis block identifier (or the `chain_id` bytes, but the identifier is derived and cannot be mistyped, #182 S-001) to the preimage, state in `bedrock-genesis-block.md` §Cryptarchia Parameters that the disjointness of networks rests on it, and add a conformance vector to `mantle-transaction-encoding.md`'s test vectors (#245, #641) so that a wallet signing for the wrong network is caught by the vectors. The wallet, the PoW claim builder, the zone SDK sequencer and the testing framework all sign through `Hashable::hash`, so the implementation is one preimage change plus the vector update.

### S-002 · Bind the ceremony's outputs to the network

`tools/blockchain-tools/src/bin/genesis.rs` derives nothing network-specific into the notes it creates; `stakeholders.yaml` is copied into the genesis transfer's output list (#201 §4). Until S-001 or the note-identifier change lands, the ceremony documentation and the tool should refuse, or at least warn on, a stakeholder file whose `(value, pk)` list has been used by another deployment (a hash of the list recorded alongside the templates is enough), because that is the exact precondition of LB-001.

### S-003 · `LeaderClaim` and the channel multi-signature operations verify their proofs twice

`LeaderClaim` verifies its Groth16 proof of claim in `preverify` (`leader_claim.rs` L225-L239, unbatched, at decode time, which #113 LB-002 shows is on the mempool's event loop) and then defers the same proof and public inputs to the block's batch (L264-L273, with a `TODO: Remove. Already checked in preverify`). `ChannelWithdraw`, `ChannelTransfer` and `ChannelConfig` verify their Ed25519 multi-signatures once in the shared helper (`verification.rs` L10-L48) and once more in their own loops (`withdraw.rs` L133-L154, `channel_transfer.rs` L164-L185; `config.rs` L148-L173 does only the loop). Keep one of each: the batch for the proof of claim (so that admission does one Groth16 at most, per #113's recommendation) and the helper for the multi-signatures, whose duplicate-index check the operations' own loops lack.

### S-004 · The "a repeated transaction conflicts with itself" rule rests on every transaction carrying a `Transfer`

`bedrock-v1.1-block-construction.md` §Reference Resolution says a transaction referenced twice "conflicts with itself, spending the same notes twice". At this commit that is true because a transaction without a `Transfer` cannot pay its fee (§4.4) and a `Transfer` must have at least one input (`ledger.rs` L291-L296). If either changes (a fee paid from a claim's balance directly, a zero-fee genesis-like path, or a `Transfer` allowed without inputs), a block could carry the same nonce-less operations twice (`ChannelInscribe` chains on its parent and would fail; `ChannelConfig` likewise; `LeaderClaim` and `ClaimPowReward` have nullifiers; `SDPDeclare` is unique by id). The rule would still hold for every current operation, but the ledger should also reject a duplicate transaction hash within a block explicitly (`try_apply_block_contents`, `ledger/src/lib.rs` L539-L546, has the hashes), so that the property does not depend on the fee model.

### S-005 · The core crate's unit tests do not compile without `--features test-utils`

`cargo test -p logos-blockchain-core --lib` at `273658c7` fails with 11 errors in `core/src/mantle/ops/transfer.rs`: `TransferOp::sample` is compiled under `#[cfg(any(test, feature = "test-utils"))]` (L71-L81) but the `Fr` and `ZkPublicKey` it uses are imported under `#[cfg(feature = "test-utils")]` alone (L2-L5), so the `test` configuration without the feature has the function and not its types. CI does not see it because `code-check.yml` L171 runs the workspace tests with `--all-features`. Either gate the imports with the same `any(test, feature = "test-utils")` predicate or move `sample` behind the feature only; a `cargo test -p logos-blockchain-core --lib` job in CI would keep the two in step. The same pattern should be grepped for across the workspace (`#[cfg(feature = "test-utils")]` on a `use` next to `#[cfg(any(test, feature = "test-utils"))]` on an item).

## Appendix A — Definitions

### A.1 Severity

| Level | Definition |
|---|---|
| **Critical** | Loss of funds, chain halt, consensus split, or deanonymisation of users, exploitable by an unprivileged network participant with modest resources. |
| **High** | As above but requires significant resources, stake, timing, or a second weakness; or a remote crash/DoS of any node from a single unauthenticated peer. |
| **Medium** | Degrades safety/liveness/privacy guarantees under realistic conditions, or DoS requiring many peers / high cost; incorrect behaviour affecting a subset of users. |
| **Low** | Limited impact or unlikely preconditions; defence-in-depth gaps; reliability issues with a security flavour. |
| **Informational** | No immediate risk but relevant to best practice, maintainability, or future changes. |
| **Undetermined** | Needs more information from the team to rate. |

### A.2 Difficulty (to exploit)

| Level | Definition |
|---|---|
| **Low** | Well-known flaw; public tools exist or exploitation can be scripted. |
| **Medium** | Attacker must write an exploit or needs in-depth knowledge of the system. |
| **High** | Requires privileged access, complex technical details, or discovery of another weakness. |
