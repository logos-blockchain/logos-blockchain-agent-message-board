## 1. Summary

- Overall assessment: the four verification keys the node embeds are exactly what the circuits pipeline claims to produce, and nothing else — `snarkjs groth16 setup` on the recompiled `v0.5.7` constraint systems and the genuine Hermez phase 1, followed by one contribution made by a GitHub Actions runner — so no substitution or tampering was found, but the keys remain a single-party phase 2 with no durable, publishable record, which `trusted-setup-ceremony.md` does not allow for production.
- Findings: 0 critical · 1 high · 0 medium · 0 low · 1 informational
- Key themes: "single-party phase 2 confirmed by independent re-verification", "the only contribution record is a CI log that expires on 2026-12-07", "development keys are not declared anywhere the node's users would look".
- Must-fix before launch: LB-001 — run the phase-2 ceremony drafted in its Recommendation for the four circuits, publish the transcript, and pin the resulting verification-key hashes in logos-blockchain.

**Description**

`trusted-setup-ceremony.md` §Overview requires that phase 2 "be securely executed for every new circuit" as a multi-party computation whose security rests on "at least one participant [who] securely deletes their secret contribution", and that "all transformations are accompanied by publicly verifiable proofs, ensuring full auditability"; §Protocol Step 4 and §Finalized CRS require erasure by each participant and publication of the final CRS with its transcript. What the node embeds was produced by:

```
ci.yml:145  snarkjs groth16 setup ${CIRCUIT_NAME}.r1cs ../${{ env.PTAU_FILE }} ${{ matrix.circuit.name }}-0.zkey
ci.yml:146  # Single-contributor trusted setup: A proper MPC ceremony is required before production (see issue #17).
ci.yml:147  head -c 32 /dev/urandom | xxd -p -c 256 | snarkjs zkey contribute ${{ matrix.circuit.name }}-0.zkey ${{ matrix.circuit.name }}.zkey --name="RELEASE" -v
ci.yml:148  snarkjs zkey export verificationkey ${{ matrix.circuit.name }}.zkey ${{ matrix.circuit.name }}_verification_key.json
```

The re-verification in §3 establishes what this means precisely for `v0.5.7`:

- The keys are consistent: each released `proving_key.zkey` verifies against the recompiled constraint system and the genuine Hermez `_17` phase 1, carries exactly one phase-2 contribution, and exports byte-for-byte the `verification_key.json` the node compiles in. Nothing foreign was inserted between the pipeline and the node.
- The keys are single-party: the one contribution was made by an ephemeral GitHub-hosted runner. `zkey verify` proves the contribution was applied correctly; it cannot prove the randomness was erased, and no party can attest to that, because no person controlled the process.
- The keys have no transcript: the contribution's identity (`RELEASE`), circuit hash and contribution hash exist only in job logs that expire on 2026-12-07. After that date the released `.zkey` is the entire record. Nothing in logos-blockchain records which verification key it expects; `Cargo.toml:172-176` names a tag, and the key arrives as bytes inside a downloaded archive (#150).
- The trust assumption resets on every tag: the job runs on every push of a `v*.*.*` tag, so `v0.5.8` will embed four new single-party keys, and every node upgrade silently switches the consensus-critical keys.

The `.ptau` is the public Hermez phase 1, which §Extending an Existing Trusted Setup Ceremony permits reusing; the deviation is confined to phase 2 and to the missing record.

**Exploit scenario**

Whoever obtained the phase-2 scalar of a circuit while it was in the runner's memory can forge a proof for any public inputs: with the PoL key, propose a block in every slot with no stake and steer the epoch nonce; with the ZkSignature key, spend any note; with the PoC key, drain the leader reward pool; with the PoQ key, bypass the blend quota. Doing so requires access to the runner at generation time or to GitHub's infrastructure, which keeps the rating at High rather than Critical. The verification performed here does not lower it: it rules out substitution of the keys, not retention of the trapdoor.

**Recommendation**
- *Short term*: run and publish the phase-2 ceremony below for the four circuits, replace the CI key-generation job by a job that consumes the ceremony output, and pin the four verification-key hashes in logos-blockchain. Until that is done, apply LB-002.
- *Long term*: separate key generation from the circuits release pipeline permanently, treat any change of a verification-key hash as a consensus-breaking change (tied to a network upgrade and a new `chain_id`), and keep a logos-blockchain CI job that re-verifies the pinned keys on every circuits tag bump.

Proposed phase-2 ceremony (per circuit; the four circuits run in parallel through the same contributor sequence). The commands are snarkjs 0.7.6, which is what the pipeline already uses; a coordinated tool such as p0tion produces the same artefacts and is acceptable if it publishes the same records.

1. Fix the inputs and publish them in the circuits repository under `ceremony/<tag>/README.md` before the first contribution:
   - the circuits tag whose sources are frozen, `circom 2.2.2`, `--r1cs --O2`, and for each circuit the r1cs sha256 and snarkjs circuit hash (for `v0.5.7` these are the values in the header of this report);
   - phase 1: `powersOfTau28_hez_final_17.ptau`, sha256 `6b662a32…`, blake2b `6247a343…`. Decision to record: the ceremony reuses this file without extension. The `_17` file has already been through `prepare phase2`; extending phase 1 as §Extending describes would mean contributing to the unprepared 2^28 transcript and re-running `prepare phase2`, which is out of proportion to circuits of 20 460 constraints;
   - the contributor list: named participants with a public signing key each (PGP or Ed25519), a minimum count and a composition rule. Proposal: at least 8 contributors, of whom at least 3 are outside Logos and the IFT (auditors, researchers, community members). The spec's threshold is one honest participant, so breadth of affiliation matters more than count;
   - the beacon: a public value that does not exist yet at announcement time, for example the drand round at a fixed future time or the hash of a Bitcoin block at a fixed future height, and the iteration count (`10` = 2^10 in snarkjs);
   - the coordinator: one named Logos engineer who relays and verifies files and is also one of the contributors.
2. Round 0 (coordinator):
   ```
   circom --r1cs --O2 <c>.circom
   snarkjs groth16 setup <c>.r1cs powersOfTau28_hez_final_17.ptau <c>_0000.zkey
   sha256sum <c>_0000.zkey            # published; deterministic, anyone can regenerate and compare
   ```
3. Round i = 1 … N (contributor i, sequentially, on a machine the contributor controls; the `contribute` step preferably offline):
   ```
   snarkjs zkey verify <c>.r1cs powersOfTau28_hez_final_17.ptau <c>_<i-1>.zkey     # verify the chain so far; abort on failure
   snarkjs zkey contribute <c>_<i-1>.zkey <c>_<i>.zkey --name="<contributor id>" -e="<own entropy>" -v
   sha256sum <c>_<i>.zkey
   ```
   The contributor records the printed contribution hash and signs an attestation containing: circuit, circuit hash, index `i`, contribution hash, sha256 of `<c>_<i>.zkey`, date, a description of the environment and of the entropy source, and a statement that the entropy and the process memory were destroyed (for example, a live system that was powered off). The coordinator runs `zkey verify` on the received file, checks that contribution `#i` in its output has the attested hash, appends the attestation and hashes to the transcript, and only then sends the file to contributor `i+1`.
4. Finalisation (coordinator, once the beacon value is public):
   ```
   snarkjs zkey beacon <c>_<N>.zkey <c>_final.zkey <beacon hex> 10 -n="Final beacon: <source>"
   snarkjs zkey verify <c>.r1cs powersOfTau28_hez_final_17.ptau <c>_final.zkey > <c>_transcript.txt
   snarkjs zkey export verificationkey <c>_final.zkey <c>_verification_key.json
   sha256sum <c>_final.zkey <c>_verification_key.json
   ```
5. Publish `ceremony/<tag>/` in the circuits repository: the README from step 1 completed with dates, the attestations, `<c>_transcript.txt` (every contribution and the beacon as `zkey verify` lists them), `SHA256SUMS` for every intermediate and final `.zkey` and for the four `verification_key.json` files, and the VK JSONs themselves. Publish the final `.zkey` files as assets of a dedicated release and mirror them on one independent host (record the content address in the README). Anyone can then repeat step 4's `zkey verify` and compare hashes.
6. Change the circuits pipeline: replace the `generate-proving-keys` job (`ci.yml:76-158`) by a job that downloads `<c>_final.zkey` and checks it against the pinned sha256, recompiles the r1cs, runs `zkey verify` (so a circuit change after the ceremony fails the build, which is how "phase 2 for every new circuit" is enforced), exports the VK, compares it to the pinned VK sha256, and only then bundles. A circuit change therefore requires a new ceremony and a network upgrade.
7. Change logos-blockchain: pin the VK hash where the key is parsed, so a wrong artefact fails at first use, and force initialisation at start-up so it fails at boot rather than at the first block. `sha2 0.10.9` is already in `Cargo.lock:7772` and only needs a workspace entry. ### LB-002 · Development-grade Groth16 keys are not declared as such in the node's security policy, README or release notes

| | |
|---|---|
| Severity | Informational |
| Difficulty | High |
| Category | Cryptography |
| Target | `SECURITY.md:1-23`; `README.md:29`; `.github/release/release-content.md:1-137` (the release body, used by `.github/workflows/prepare-release.yml:171`) |
| Status | Open |

**Description**

The only statements that the keys are not production keys are a comment in the circuits pipeline (`ci.yml:146`) and circuits issue `#17`. Neither is visible from the node repository, its releases or its security policy, which are what operators, validators and integrators read. `SECURITY.md` covers supported versions and vulnerability reporting only. `README.md:29` describes the circuits as "Downloaded via setup script (see below)", which is stale (no such script exists; the `lbc-*-sys` build scripts download the archive) and says nothing about the keys. The release body template `.github/release/release-content.md` and the RC disclaimer mention neither the keys nor that every circuits tag bump replaces them. Release `0.2.4`, presented as the client for the public testnet, therefore gives no indication that block production, note spending, reward claims and blend quotas rest on keys whose trapdoor was in one CI runner's memory, nor which key hashes a build is expected to contain.

**Exploit scenario**

None directly. The gap matters when someone relies on the testnet or an early mainnet build as if the specified ceremony had happened, or when a key hash changes between releases and nobody notices because no expected value was ever stated.

**Recommendation**
- *Short term*: add a "Cryptographic parameters" section to `SECURITY.md` stating that the Groth16 proving and verification keys for circuits `v0.5.7` were generated by a single-party setup in CI, are development keys, will be replaced by the output of the ceremony in LB-001 before any production network, and listing the four verification-key sha256 values from this report's header so that a build can be checked against them. Add one sentence with the same statement to `.github/release/release-content.md`, and correct `README.md:29`.
- *Long term*: once LB-001 is done, replace the section with a link to the ceremony transcript and the pinned hashes, and keep the release body stating the circuits tag and VK hashes each release embeds.

**References**: circuits `ci.yml:146`; circuits issue `#17`; `inbox/64-zk-integration.md` LB-001 (recommended the same notice).

### S-001 · The circuits tag names a commit made after the one the keys were built from

| | |
|---|---|
| Category | Maintainability |
| Target | `Cargo.toml:172-176` (`tag = "v0.5.7"`), `Cargo.lock:4385`, `flake.lock:27`; circuits `.github/workflows/ci.yml:1447-1495` |

**Description**

The `Update Nix Hashes` job commits `circuits-nix-hashes.json` after the release is published and force-moves the tag onto that commit (`ci.yml:1494-1495`). For `v0.5.7` the keys were generated by run `34236897106` at `e97ab1f`, while the tag, `Cargo.lock:4385` and `flake.lock:27` all name `ebf7ddf`. `gh run list --commit ebf7ddf` finds no CI run, so a reproducer starting from the pinned commit has to know to look one commit back; a force-moved tag also means `tag = "v0.5.7"` in `Cargo.toml` can resolve to different commits at different times, with only `Cargo.lock` fixing it. Either commit the hashes before tagging (build from a candidate tag, then tag the hash commit once), or add `rev = "<sha>"` next to `tag` in `Cargo.toml:172-176` so the pin is explicit in the source and not only in the lockfile.

|---|---|
| **Critical** | Loss of funds, chain halt, consensus split, or deanonymisation of users, exploitable by an unprivileged network participant with modest resources. |
